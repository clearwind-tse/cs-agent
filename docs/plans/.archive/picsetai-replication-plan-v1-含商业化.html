01一句话结论

PicsetAI 不是一个「AI 生图工具」，而是一条电商视觉的生产流水线：用 LLM 把「一张商品图」翻译成「可编辑的设计规划」，再用图生图模型批量执行，最后用一块画布兜住二次修改。

护城河 ①：两阶段生成

分析 → 人工确认规划 → 批量出图。既降低废片率（省积分 = 省成本），又把"抽卡"变成"审稿"，这是它相对通用生图产品的核心体验差。

护城河 ②：提示词资产

约 40 组模板（组图分析 / SKU 三种替换 / 服装统一分析 / 模特策略 / 精修分析 / 分镜…），支持版本、diff、回滚、灰度、分区域分语言。这是最难被抄走的部分。

护城河 ③：白标底座

同一套前端按品牌配置切换（picsetai-cn / liuyingai / pixmall-cn），连模型名称都可改（Nano Banana → Nova 2.0）。一套代码卖多个站。

复刻判断：功能层面 8–10 周可做到 80% 可用（商品套图 + 风格复刻 + 画布 + 积分）；但「一次成片率」取决于提示词与测试集积累，需要 3–6 个月的品类样本喂养。不要按"功能清单"排期，要按"质量爬坡"排期。

3.1 全品类商品图 —— 全站的原型

复刻要点：①「确认规划」这一屏是产品灵魂——它把不可控的抽卡变成可审的稿件，务必做成可逐字段编辑，而不是只读预览。②分析结果必须是严格 JSON（{design_specs, images:[{title,description,design_content,product_index,aspect_ratio}]}），前端要能容错（先试 JSON.parse，失败再抓 {...}/[...] 片段，再失败就把原文当 design_specs 直接展示）。③把"消耗 N 积分"写在确认按钮上，转化率与投诉率都会更好。

3.2 风格复刻 + SKU 替换 —— 商业化最强的一环

三个 tab 共享同一套上传区（参考图 + 产品图），差异在"分析器"和"输出组织方式"：

Tab输入行为输出
单图复刻1 参考图 + 1 产品图 + 特殊需求提取参考图设计语言，套到产品上N 张同风格图
批量复刻多参考图 × 多产品图按组配对，批量提交按组分组展示
SKU 替换1 参考图 + ≤20 张 SKU 图（每张可填颜色/尺码/规格）只换主体与产品名称，背景、构图、排版、字体全部保留按 SKU 1..N 分组，全部下载

SKU 替换下面还挂三种分析器，这是它真正的技术分层：

  • 智能替换：整图理解后重新生成，一致性最好、成本最高。
  • 局部替换：先定位产品在参考图中的位置与尺度，只重绘该区域，其余像素保持——最省积分，也最容易露馅（边缘、投影）。
  • 多场景替换：一次任务喂多个场景，输出多场景成套。
隐藏机制："专家模式"另有一套分析模型（expert_analysis_credit_cost），按每个新分析任务收费，成功分析结果复用不重复收费。这条规则很重要——它把"分析"当资产缓存，而不是每次重算，既省钱又提升一致性。
复刻要点：SKU 场景的正确解法不是"让模型自己保持一致"，而是 参考图锁定 + 区域掩膜 + 提示词只描述变量。要单独建一张 sku_items 表存每个 SKU 的参数文本，生成时拼进 特殊需求 段，而不是让用户写一段长 prompt。

3.3 服装组图 —— 最复杂、也最能拉开差距

链路比商品图长一层：统一分析 → 策略选择 → 分镜/套图 → 逐镜生成。

  • 统一分析：解析版型、面料、工艺细节、色彩，产出一份"服装统一分析"（中英双版提示词）。
  • 策略：品牌大片（棚拍、硬光、杂志感）或 手机网感（生活化、随手拍、UGC 感）——两条完全不同的提示词路径。
  • 套图类型：模特试穿、白底图、人台图、3D 立体图、细节特写、卖点图、三视图（有参考人物 / 无参考人物两套生成器）。
  • 模特：模特描述生成 → 三视图模特图 → 与服装合成。场景侧有「场景推荐」+「场景生图」+ 场地历史库（clothing_scene_history）。

逐镜提示词的拼装顺序（逆向出的骨架，几乎可以直接用）：

// 每一张图的最终 prompt
【核心指令】目标输出语言：{targetLangName}。
【整体设计规范】{designSpecs}
【本镜：{shot.title}】{shot.description}
{shot.markdownContent}

// 然后追加 5 条一致性锁
modelIdentityLock   // 模特身份只来自参考图，不得漂移
fullOutfitLock      // 整套服装（含配饰）不得增删改
sceneLock           // 场景一致性（有场景参考图时）
photorealism        // 真实感约束
finalIdentityReminder // 结尾再强调一次：出现的人只是"衣架"，脸不属于输出
最后那条是本方案里最聪明的一处工程细节：他们把"人脸身份"和"服装身份"显式解耦，并在提示词末尾再重复一次（模型对结尾指令的服从度更高）。做虚拟试衣时，这一条能显著降低"换了个模特"的投诉。

3.4 图片精修 / 批量抠图 / 批量翻译

图片精修

双分析器：精修分析-GPT Image 2 与 精修分析-Nano Banana 两套提示词，按所选模型走不同分析路径（不同模型对"瑕疵"的理解不一样）。分析产出逐图精修指令，再批量执行。附带"去精修获得白底图"——白底图是 SKU 替换与批量抠图的输入端。

批量抠图

走火山 veImageX，不走生成模型（快且便宜）。计费单位是「每积分成功次数」而不是"每张积分"，失败不扣——这是对用户体验更友好的计价方式，也避免了"扣了钱没结果"的退款工单。

批量翻译是唯一"非生成"的视觉任务：千问 OCR 抽字（独立 QPS 队列，配 0 即关闭该能力）→ LLM 翻译 → 在原文字框内重绘。难点全在版式还原：字号要按原框宽度自适应，长英文必须缩字号或换行，否则一定溢出。复刻时给它单列一条"文字排版约束"提示词，不要塞进通用模板。

3.5 万能画布 —— 决定留存的那块板

纯前端（fabric.js）+ 少量服务端能力。功能密度全站最高：

图层系统

图层树、多选、打组/解组、锁定、层级上移下移置顶置底、对齐、拖拽缩放旋转、画布缩放/小地图/取色。

智能分层

1.0 = 图像分割；2.0 = 区域框选 / 智能识别 / 自然语言描述主体。按层计费，提交时按"最大层数 × 单价"预占，完成后按实际层数多退少补。

文字工具

字体库（思源黑/宋、阿里普惠体、仓耳系列、站酷系列）、字号、字距、行高、对齐、颜色、描边、字符面板。

AI 编辑

去背景、分割图片、裁剪、画笔、框选标注（矩形/箭头/文字/自由画笔）。

反推提示词

把画布上的图反解成提示词，接着改（canvas_reverse_prompt_credit_cost）。

导出

PNG 导出、打包下载、PSD 导出（自研 8BPS 写入，保留图层）、合并图层后导出。

标注 → 提示词的转换（这是"局部重绘"的关键实现）

用户在图上画框/箭头/写字，系统不截图给模型，而是把标注序列化成归一化坐标文本注入 prompt：

[图片标注说明] 第 1 张参考图为无标注的原始商品图，是生成主体。
第 2 张参考图（若提供）仅用于理解标注的空间位置；其中的线条、矩形框、
箭头与文字是编辑指令，严禁出现在最终商品图中。
坐标均为相对原图宽高的归一化值（0–1），原点左上。
标注1 矩形 [x=0.312, y=0.488, w=0.221, h=0.164]：标记需修改或关注的区域（框线不是商品图案）。
标注2 文字「把背景换成米白色」位于 (0.500, 0.820)：该文字是编辑指令，不要当作商品上原有的印刷文案渲染。
复刻要点：既传"原图"又传"带标注的合成图"两张参考，并在提示词里显式声明哪张是主体、线条不是图案。少了这句，模型十次有三次会把红框画进图里。

3.6 视频工坊 —— 图片能力的延展，不是新品类

01脚本输入商品信息 → 脚本解析（canvas_parse_script_credit_cost，0 = 免费）→ 生成多条文字分镜方案。
02分镜选一套分镜方案，逐镜生成画面；多宫格分镜会把多镜合成一张带序号的标记图再送回模型，用来保持镜头间的连续性（合成失败会回退发无标记原图，并在日志里说明"识别准度会下降"）。
03生成Seedance 2.0：首帧模式（1 张）/ 首尾帧模式（2 张）/ 全能参考；按 模型 × 分辨率 × 秒 计费，参考视频另计 reference_video_credits_per_sec。
04后处理去字幕（仅 Seedance 产物）、一键高清（按分钟计费，四舍五入且至少 1 积分）、回调 video-seedance-callback 异步落库。

工程上有两处值得抄：① 原始视频链接 24 小时过期，必须尽快转存到自有 OSS，否则用户第二天回来看到的是空图；② 视频时长、并发、任务硬超时（1800 秒上限）全部在后台可配，不在前端写死。

3.7 账户、积分与支付

  • 登录：邮箱密码 / 手机号验证码（仅国内站）/ 微信扫码 / 快速登录 / 企微绑定（绑定送积分）/ 邀请码门控（可强制）。人机验证走网易易盾 + 阿里云验证码 2.0 双通道。
  • 积分三类：购买（永久）/ 订阅（永久）/ 赠送。扣减用 deduct_credits_with_priority 按优先级顺序扣，避免"赠送积分永不过期而付费积分先过期"这类账务坑。
  • 预占-结算：提交时预占（按最大可能消耗），完成时按实际结算，多退少补；失败释放预占；超时强制取消并退款。
  • 支付：支付宝直连、付呗（订阅周期扣款/分期）、易宝聚合（微信+支付宝）、可配微信小程序内唤起。支付成功靠 Supabase Realtime 监听 credit_purchases 行变更 + 15 分钟轮询兜底（间隔 3s 起、×1.5 指数退避、上限 15s） 双保险。
  • 子账号：主账号可开子账号、分配/回收积分、设备注、看团队工作流；代理商体系单独一套角色。

  1. 模型路由层：统一入参（模型逻辑名 / 档位 / 比例 / 清晰度 / 参考图数组），内部映射到不同上游的协议差异（Gemini 原生 vs OpenAI 兼容 vs 火山方舟），带权重分流、失败降级、错误分类、耗时与成本埋点。

-- 用户与账户

  id uuid primary key,

);

-- 产物：一个 job 出 N 张
create table generations (
  id uuid primary key,
  job_id uuid references generation_jobs(id),
  idx int, status text,      -- pending|generating|done|failed
  image_url text, thumb_url text,
  width int, height int,
  title text, subtitle text, design_content text,   -- 供画布二次编辑

06生成流水线

这是复刻的核心工程量。看上去是"调 API 出图"，实际有 4 层状态、3 种重试、2 次计费、1 个确认闸门。

6.1 状态机

queued ──▶ analyzing ──▶ awaiting_confirm ──▶ generating ──┬─▶ completed
   │            │                 │                  │      ├─▶ partial_failed（单张失败，可单张重试）
   │            │                 │                  │      └─▶ failed（全失败，释放预占）
   └────────────┴─────────────────┴──────────────────┴─▶ canceled / timeout
                                                        （1800s 硬超时）
  • 预占发生在 queued：先扣后跑，避免"跑完不付钱"；失败/取消/超时必须释放。
  • awaiting_confirm 是人工闸门：需要前端心跳保活，超时自动取消并退款（否则用户关页面，任务挂在半空）。
  • partial_failed 不等于失败：已出的图照常交付与结算，未出的单独退。这一条能把退款率拉低一个量级。

6.2 一次批量生成的时序

  1. 前端生成 client_job_id（UUID），调 create-job，服务端先做幂等判断。
  2. 事务内：查余额 → 预占 → 建 job → 返回 job_id + 预占积分。
  3. 执行器取任务：调 LLM（分析）→ 写 design_specs + design_content → 状态置 awaiting_confirm，Realtime 推送。
  4. 用户确认（可改任意字段）→ 状态置 generating。
  5. 按图片规划切 N 个子任务，进队列，按 batch_concurrency 并发；每个子任务：编译 prompt → 路由选供应商 → 调用 → 下载转存 OSS → 写 generations → 推送。
  6. 全部结束：按实际成功张数结算（多退少补），写 credit_ledger，状态定稿。
三个必须做的防呆：① 上游返回的临时链接 必须立刻转存（多数只活 24h）；② 单张重试要有上限（建议 2 次）且退避，否则一次故障能把余额烧穿；③ 结算时读的是「当前」价格表而不是提交时的快照——所以要在 job 里存一份价格快照，否则调价那天会算错账。

6.3 一致性：三个可落地的技术手段

参考图编排

固定语义顺序：第 1 张永远是"无标注原始商品图 = 生成主体"，第 2 张才是"带标注的编辑指令图"，并在 prompt 里显式声明。顺序错了，主体就会被参考图带跑。

提示词锚定

把"不可变"的部分（品牌色、LOGO、材质、型号文字）写成"硬约束段"，放在 prompt 首尾各一次；把"可变"的部分（场景、文案）写成占位符。

出图后质检

用视觉模型回读成品，比对"主体轮廓 / 关键文字 / 主色"三项，不达标自动重跑一次并记录。这是把废片率从 30% 压到 10% 的唯一办法。

07提示词资产体系

这是最不像"代码"、但最决定成败的部分。他们把它做成了可运维的系统：模板 + 变量 + 池 + 分区域分支 + 版本回滚。

7.1 三层结构

第一层：骨架模板（决定结构）
电商/社交 · 整体规范模板
  变量：{aspectRatioLine} {typeGoal} {requirement} {productSummaryLine}
        {globalRulesLine} {copyBankLine} {fidelityLine} {multiImageDiffRule} {textRule}

  变量：{role} {visual} {layout} {camera} {copyLine} {bodyQuality} {multiDrawSuffix}

第二层：池（决定多样性，每行一项，按 index 轮播）

产品保真规则 · 多图差异规则 · 单张收尾规则 · 无文字纯视觉规则
有目标语言时的文字要求 · 活动海报的文字克制规则 · 多语言排版约束

7.2 一条约束能省多少事

抄一段他们写在模板里的规则结构（复刻时直接照这个粒度写）：

## 1. 产品保真
· 商品主体的形状、比例、颜色、材质纹理、LOGO、型号文字，必须与参考图完全一致。
· 允许改变：环境、光线方向与强度、投影、背景、周围道具。
· 禁止改变：商品结构、配件数量、包装上的文字内容。

## 2. 多图差异
· 同一批 N 张图之间，构图、镜头、场景、文案必须至少 3 项不同。
· 禁止把同一张构图换配色重复输出。

## 3. 单张收尾
· 每张图必须自洽：有视觉重心、有留白、文字不压主体、无裁切错误。
· 文字层级清晰：主标题 > 副标题 > 说明文字，字号比约 3 : 1.8 : 1。
为什么要"版本 + diff + 回滚"：提示词是会回归的。今天为 A 品类加的约束，明天会让 B 品类翻车。没有版本控制，你只能靠记忆和截图；有了它，一次调崩可以在 1 分钟内退回上一版。他们把 diff 做到了逐行红绿对比 + 保存前确认，这是工程团队该有的克制。

7.3 测试集：比模板更重要

建议第一天就建一个 30 个 SKU × 5 个品类的固定测试集（家居 / 服饰 / 3C / 美妆 / 食品），每次改提示词或换模型，跑一遍打分：主体保真、文字正确率、版式合规、可用率（人工 1–5 分）。没有这个，所有"效果优化"都是玄学。

#难点表现破解

4规划 JSON 不稳定模型输出带 markdown 包裹、字段缺失强 schema + few-shot + 容错解析（parse→正则截取→降级纯文本）+ 失败重试 1 次

11不要照抄的地方

原产品有 13 个模块，是因为它要覆盖所有人的需求（也为了让 SEO 页更多）。你新做，抄全 = 每个都做不深。

① 选一个垂类做深，而不是全品类

家居、饰品、服装三个品类的"保真难点"完全不同。全品类意味着你的提示词要兼容一切，结果是谁都不够好。建议先锁 1–2 个品类，把可用率做到 75%+ 再扩。

② 把"交付物"做厚

原产品给的是图片。你可以给：平台尺寸包（一次导出淘宝 3:4 + 抖音 9:16 + 亚马逊 A+ 全套）、文案 CSV、可编辑 PSD、甚至详情页 HTML。同价位下这是最容易感知的差异。

③ 用"一次成片率"做北极星，而不是"生成张数"

张数是成本，成片率才是价值。把首页数字改成"你这次省了几次返工/几小时"，比"已生成 1 亿张"更有说服力。

④ 不要做分销，先做口碑

分销适合已有流量池的团队。冷启动阶段，返佣的钱不如投在"100 个种子卖家免费用 + 一对一出图"。他们的代理门槛是"转化 5 个付费用户"，说明这套是给已有渠道的人用的。

⑤ 与既有系统打通是你的独有优势

如果团队已有客服/CRM/订单系统，把"商品图生成"接进"上新流程"——运营在商品后台点一下，图就回来了。这是纯工具型产品做不到的护城河。

⑥ 视频不要早做

视频单价高、失败率高、审核严，且用户对"能看"的容忍度远低于图片。等图片业务跑正毛利、有稳定现金流再上。

定位建议（一句话）

不做"又一个 AI 商品图工具"，做「某品类的详情页生产线」：上传一张实拍，输出一套可直接上架、可二次编辑、带平台尺寸与合规检查的完整素材包。
差异点不在模型（大家都能调），在于"这个品类的知识"——什么角度显质感、什么文案能过审、什么比例不被限流。

B附录：验收用例

  1. 重复提交：同一 client_job_id 连点 5 次，只生成 1 个 job、只扣 1 次积分。
  2. 分析失败：LLM 返回非 JSON / 超时，前端展示可重试态，预占积分全额释放。
  3. 确认页超时：停在"确认规划"10 分钟不回，任务自动取消并退款。
  4. 部分失败：4 张里 1 张失败，交付 3 张、按 3 张结算、单张可重试。
  5. 供应商故障：主链路 500，自动切兜底链路，用户侧只见"稍慢"，最终成功。
  6. 产物过期：24 小时后回看历史，图片仍可访问（已转存自有存储）。
  7. 调价：提交时 A 价、完成时已调为 B 价，按 A 价结算（job 存价格快照）。
  8. 审核命中：上传违规图，前端明确提示、积分退回、日志可查。
  9. SKU 20 张：全部成功；结果按 SKU 分组；打包下载 zip 命名规则正确。
  10. 画布恢复：刷新页面后图层、位置、文字内容完整恢复（快照可用）。
