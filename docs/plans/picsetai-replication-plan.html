01一句话结论

PicsetAI 不是一个「AI 生图工具」，而是一条电商视觉的生产流水线：用 LLM 把「一张商品图」翻译成「可编辑的设计规划」，再用图生图模型批量执行，最后用一块画布兜住二次修改。

核心机制 ①：两阶段生成

分析 → 人工确认规划 → 批量出图。既降低废片率（省的是时间和调用费），又把"抽卡"变成"审稿"。这是它相对通用生图产品最实质的体验差，也是开源版最该抄的一处。

核心机制 ②：提示词资产

约 40 组模板（组图分析 / SKU 三种替换 / 服装统一分析 / 模特策略 / 精修分析 / 分镜…），带版本、diff、回滚、分区域分语言。这是最难被抄走、也最适合开源共建的部分。

核心机制 ③：配置化模块

详情 16 模块 + 主图 5 模块都是后台数据，勾选即上架、写子提示词即改行为。开源版保留这条通道，等于给社区留了「不改代码就能加功能」的入口。

复刻判断：功能层面 8–10 周可做到 80% 可用（商品套图 + 风格复刻 + 画布 + 配额）；但「一次成片率」取决于提示词与测试集积累，需要 3–6 个月的品类样本喂养。不要按"功能清单"排期，要按"质量爬坡"排期。

每个模块给四件事：流程（用户看到什么）、参数面板（有哪些旋钮）、隐藏机制（不写在界面上但决定体验的部分）、复刻要点。

3.1 全品类商品图 —— 全站的原型

01输入产品图 0/6（多图上传有"不是越多越好"的提示）、主图 / 详情图二选一、目标平台（智能匹配 / 淘宝 / 天猫 / 拼多多 / 京东 / 抖音 / 亚马逊 / TEMU / eBay / SHEIN / Shopee / Lazada / TikTok）、主图要求或详情要求（自然语言）、AI 帮写、目标语言（含"无文字（纯视觉）"）、模型、尺寸比例、清晰度、生成数量、速度档。
02分析中按钮变"分析中"，禁止重复提交；服务端跑 LLM，产出结构化 JSON。
03确认规划（关键一步）左「整体设计规范」六段：字体系统（标题思源宋体 / 正文思源黑体 / 字号 3:1.8:1）、视觉语言（装饰元素、图标风格、留白 ≥30%）、摄影风格（光线、景深、相机参数 f/8 · 1/125s · ISO100）、品质要求、目标平台、图片规划；右「共 N 张」逐张标题 + 描述 + 展开的 design_content，每张都能改。
04生成中占位卡逐张替换，单张失败不影响整组（partial_failed）。
05完成批量下载 / 单张下载 / 进画布二次编辑 / 换风格重跑。

3.2 风格复刻 + SKU 替换 —— 复用价值最高的一环

三个 tab 共享同一套上传区（参考图 + 产品图），差异在"分析器"和"输出组织方式"：

Tab输入行为输出
单图复刻1 参考图 + 1 产品图 + 特殊需求提取参考图设计语言，套到产品上N 张同风格图
批量复刻多参考图 × 多产品图按组配对，批量提交按组分组展示
SKU 替换1 参考图 + ≤20 张 SKU 图（每张可填颜色/尺码/规格）只换主体与产品名称，背景、构图、排版、字体全部保留按 SKU 1..N 分组，全部下载

SKU 替换下面还挂三种分析器，这是它真正的技术分层：

  • 智能替换：整图理解后重新生成，一致性最好、耗时最长。
  • 局部替换：先定位产品在参考图中的位置与尺度，只重绘该区域，其余像素保持——最快最省，也最容易露馅（边缘、投影）。
  • 多场景替换：一次任务喂多个场景，输出多场景成套。
原站的商业包装（本方案不实现）：SKU 分析按"每个新任务"计费、成功分析复用不重复收费。这套"分析结果当资产缓存"的思路在开源版同样有用——不是省钱，而是省一遍 3 分钟的等待，所以仍建议缓存分析结果。
复刻要点：SKU 场景的正确解法不是"让模型自己保持一致"，而是 参考图锁定 + 区域掩膜 + 提示词只描述变量。要单独建一张 sku_items 表存每个 SKU 的参数文本，生成时拼进「特殊需求」段，而不是让用户写一段长 prompt。

3.3 服装组图 —— 最复杂、也最能拉开差距

链路比商品图长一层：统一分析 → 策略选择 → 分镜/套图 → 逐镜生成。

  • 统一分析：解析版型、面料、工艺细节、色彩，产出一份"服装统一分析"（中英双版提示词）。
  • 策略：品牌大片（棚拍、硬光、杂志感）或 手机网感（生活化、随手拍、UGC 感）——两条完全不同的提示词路径。
  • 套图类型：模特试穿、白底图、人台图、3D 立体图、细节特写、卖点图、三视图（有参考人物 / 无参考人物两套生成器）。
  • 模特：模特描述生成 → 三视图模特图 → 与服装合成。场景侧有「场景推荐」+「场景生图」+ 场地历史库。

逐镜提示词的拼装顺序（逆向出的骨架，几乎可以直接用）：

// 每一张图的最终 prompt
【核心指令】目标输出语言：{targetLangName}。
【整体设计规范】{designSpecs}
【本镜：{shot.title}】{shot.description}
{shot.markdownContent}

// 然后追加 5 条一致性锁
modelIdentityLock   // 模特身份只来自参考图，不得漂移
fullOutfitLock      // 整套服装（含配饰）不得增删改
sceneLock           // 场景一致性（有场景参考图时）
photorealism        // 真实感约束
finalIdentityReminder // 结尾再强调一次：出现的人只是"衣架"，脸不属于输出
最后那条是本方案里最聪明的一处工程细节：他们把"人脸身份"和"服装身份"显式解耦，并在提示词末尾再重复一次（模型对结尾指令的服从度更高）。做虚拟试衣时，这一条能显著降低"换了个模特"的失败率。

3.4 图片精修 / 批量抠图 / 批量翻译

图片精修

双分析器：精修分析-GPT Image 2 与 精修分析-Nano Banana 两套提示词，按所选模型走不同分析路径（不同模型对"瑕疵"的理解不一样）。分析产出逐图精修指令，再批量执行。附带"去精修获得白底图"——白底图是 SKU 替换与批量抠图的输入端。

批量抠图

走图像处理接口而不是生成模型（快、便宜、稳）。开源版可以先用本地 rembg（U2-Net）兜底，效果不够再接商业 API——这是社区部署最关心的一点：不强制联网付费。

批量翻译是唯一"非生成"的视觉任务：OCR 抽字（独立 QPS 队列，配 0 即关闭该能力）→ LLM 翻译 → 在原文字框内重绘。难点全在版式还原：字号要按原框宽度自适应，长英文必须缩字号或换行，否则一定溢出。复刻时给它单列一条"文字排版约束"提示词，不要塞进通用模板。

3.5 万能画布 —— 决定留存的那块板

纯前端（fabric.js）+ 少量服务端能力。功能密度全站最高：

图层系统

图层树、多选、打组/解组、锁定、层级上移下移置顶置底、对齐、拖拽缩放旋转、画布缩放/小地图/取色。

智能分层

1.0 = 图像分割；2.0 = 区域框选 / 智能识别 / 自然语言描述主体。每次分层产出一组图层 + 一个 PSD 结构。

文字工具

字体库（思源黑/宋、阿里普惠体、仓耳系列、站酷系列）、字号、字距、行高、对齐、颜色、描边、字符面板。

AI 编辑

去背景、分割图片、裁剪、画笔、框选标注（矩形/箭头/文字/自由画笔）。

反推提示词

把画布上的图反解成提示词，接着改。

导出

PNG 导出、打包下载、PSD 导出（保留图层）、合并图层后导出。

标注 → 提示词的转换（这是"局部重绘"的关键实现）

用户在图上画框/箭头/写字，系统不截图给模型，而是把标注序列化成归一化坐标文本注入 prompt：

[图片标注说明] 第 1 张参考图为无标注的原始商品图，是生成主体。
第 2 张参考图（若提供）仅用于理解标注的空间位置；其中的线条、矩形框、
箭头与文字是编辑指令，严禁出现在最终商品图中。
坐标均为相对原图宽高的归一化值（0–1），原点左上。
标注1 矩形 [x=0.312, y=0.488, w=0.221, h=0.164]：标记需修改或关注的区域（框线不是商品图案）。
标注2 文字「把背景换成米白色」位于 (0.500, 0.820)：该文字是编辑指令，不要当作商品上原有的印刷文案渲染。
复刻要点：既传"原图"又传"带标注的合成图"两张参考，并在提示词里显式声明哪张是主体、线条不是图案。少了这句，模型十次有三次会把红框画进图里。

3.6 视频工坊 —— 图片能力的延展，不是新品类

01脚本输入商品信息 → 脚本解析 → 生成多条文字分镜方案。
02分镜选一套分镜方案，逐镜生成画面；多宫格分镜会把多镜合成一张带序号的标记图再送回模型，用来保持镜头间的连续性（合成失败会回退发无标记原图，并说明"识别准度会下降"）。
03生成Seedance 2.0：首帧模式（1 张）/ 首尾帧模式（2 张）/ 全能参考；按 模型 × 分辨率 × 秒 计价。
04后处理去字幕（仅支持部分模型产物）、一键高清、回调异步落库。

工程上有两处值得抄：① 上游原始视频链接 24 小时过期，必须尽快转存到自有存储，否则用户第二天回来看到的是空图；② 视频时长、并发、任务硬超时（1800 秒上限）全部可配，不在前端写死。

开源版建议把视频放到最后：单价高、失败率高、审核严，且用户对"能看"的容忍度远低于图片。等图片链路稳定再说。

3.7 账户、准入与配额（替代原站的积分体系）

原站这一层是「登录 + 积分 + 支付」。开源版没有钱，但仍然需要一个闸门——否则别人部署在公网的实例会被爬成免费 API。三件事就够：

① 身份：可有可无

AUTH_MODE=none（纯本地单人，无登录）/ local（本地账号密码，Postgres 存 hash）/ oidc（接企业 SSO）。默认 none，让"docker compose up 就能用"成立。

② 准入：一道口令

ACCESS_CODE 环境变量。公网部署时前端先验证口令、后端校验签名 cookie。一个变量挡住 95% 的滥用，比做注册体系便宜得多。

③ 配额：按张数不按钱

quota_policy 配置每日张数、单次批量上限、并发 job 数。不存在余额概念，只有"今天还能出多少张"。超限给明确提示，不是报错。

原站怎么做（仅供参考，不复刻）：积分分购买 / 订阅 / 赠送三类，按优先级扣减；提交时按最大消耗预占，完成后按实际多退少补；支付靠数据库行变更订阅 + 轮询兜底。唯一值得借鉴的是"预占"这个动作——开源版可以借它做"配额预留"，避免并发超发（见 6.1）。

3.8 后台：一个"什么都能改"的配置中枢

分区能改什么为什么重要
提示词约 40 组模板，按 key 编辑，带版本历史、diff 逐行对比、回滚、区域/语言分支、生效开关唯一能"改效果不改代码"的地方

04架构与部署形态

原站把后端整个交给 Supabase，是「3 人团队省掉后端」的解法。开源项目目标不同：别人一条命令能跑起来，且不依赖任何付费托管服务。

4.1 还原出的原站拓扑

4.2 开源版架构：一个 compose 文件起全栈

# docker-compose.yml（骨架）
services:
  db:     { image: postgres:16, volumes: ["pgdata:/var/lib/postgresql/data"] }
  queue:  { image: redis:7 }

三条硬约束（写进 README，也写进 PR 检查）：
① 零付费服务依赖：不填任何 Key 也能起、能进站、能看示例；填了 Key 才能生成。
② 密钥只走环境变量或加密存储：绝不写进前端 bundle、绝不写进日志（日志里出现 key 直接打码）。
③ 单机可跑：Postgres + Redis 都能退化成"单机默认"；不强制 S3、不强制任何云函数。

4.4 三个必须自研的部件

  1. 模型路由层：统一入参（模型逻辑名 / 档位 / 比例 / 清晰度 / 参考图数组），内部吃掉不同上游的协议差异（Gemini 原生 vs OpenAI 兼容 vs 火山方舟），带权重分流、失败降级、错误分类、耗时埋点。
  2. 提示词编译层：模板 + 变量 + 池 + 区域/语言分支 → 最终 prompt。必须是纯函数、可单测、可 diff。这是开源项目接受 PR 最多的地方。
  3. 任务执行器：一个 run_job(job_id) 函数跑完整个链路，不依赖任何框架魔法。换队列、换数据库都不用改业务。

06生成流水线

这是复刻的核心工程量。看上去是"调 API 出图"，实际有 4 层状态、3 种重试、1 个确认闸门、1 套配额预留。

6.1 状态机

queued ──▶ analyzing ──▶ awaiting_confirm ──▶ generating ──┬─▶ completed
   │            │                 │                  │      ├─▶ partial_failed（单张失败，可单张重试）
   │            │                 │                  │      └─▶ failed（全失败，释放预留）
   └────────────┴─────────────────┴──────────────────┴─▶ canceled / timeout（1800s 硬超时）
  • 配额预留发生在 queued：按"最大可能张数"先占，防止并发把当日额度打穿；完成或失败时释放/结转。这和积分"预占-结算"是同一件事，只是单位从钱变成张。
  • awaiting_confirm 是人工闸门：需要前端心跳保活，超时自动取消并释放预留（否则用户关了页面，任务挂在半空一直占着额度）。
  • partial_failed 不等于失败：已出的图照常交付，未出的单独重试或放弃。

6.2 一次批量生成的时序

  1. 前端生成 client_job_id（UUID），调 POST /jobs，服务端先做幂等判断。
  2. 事务内：查当日配额 → 预留 → 建 job → 返回 job_id。额度不足直接 429 + 明确文案（"今日还剩 3 张，本次需要 4 张"）。
  3. worker 取任务：调 LLM（分析）→ 写 design_specs + design_content → 状态置 awaiting_confirm，SSE 推给前端。
  4. 用户确认（可改任意字段）→ 状态置 generating。
  5. 按图片规划切 N 个子任务进队列，按 batch_concurrency 并发；每个子任务：编译 prompt → 路由选供应商 → 调用 → 下载转存 → 写 generations → 推送。
  6. 全部结束：按实际成功张数结转配额，状态定稿，成本汇总写回 job。
三个必须做的防呆：① 上游返回的临时链接必须立刻转存（多数只活 24h）；② 单张重试要有上限（建议 2 次）且退避，否则一次故障能把一天额度烧穿；③ worker 崩溃后要能捡回"卡在 generating 的 job"——用 updated_at 超时扫描，标记失败并释放预留。

6.3 一致性：三个可落地的技术手段

参考图编排

固定语义顺序：第 1 张永远是"无标注原始商品图 = 生成主体"，第 2 张才是"带标注的编辑指令图"，并在 prompt 里显式声明。顺序错了，主体就会被参考图带跑。

提示词锚定

把"不可变"的部分（品牌色、LOGO、材质、型号文字）写成"硬约束段"，放在 prompt 首尾各一次；把"可变"的部分（场景、文案）写成占位符。

出图后质检

用视觉模型回读成品，比对"主体轮廓 / 关键文字 / 主色"三项，不达标自动重跑一次并记录。这是把废片率从 30% 压到 10% 的唯一办法。

07提示词资产体系

这是最不像"代码"、但最决定成败的部分。它必须做成可运维的系统：模板 + 变量 + 池 + 分区域分支 + 版本回滚。

7.1 三层结构

第一层：骨架模板（决定结构）
电商/社交 · 整体规范模板
  变量：{aspectRatioLine} {typeGoal} {requirement} {productSummaryLine}
        {globalRulesLine} {copyBankLine} {fidelityLine} {multiImageDiffRule} {textRule}

电商/社交 · 单张设计模板
  变量：{role} {visual} {layout} {camera} {copyLine} {bodyQuality} {multiDrawSuffix}

第二层：池（决定多样性，每行一项，按 index 轮播）
版式池：居中英雄构图 / 对角线景深 / 左右分栏 / 上图下文 / 多信息卡片 / 拼贴网格 …
镜头池：正面平视商业摄影 / 45° 侧前方英雄位 / 冲击力近景 / 超近局部特写 / 低机位仰拍 …
光线池：柔光棚拍 / 硬光强阴影 / 自然生活光 / 浅景深层次 / 前景遮挡层次 …
文案池：标题参考 / 卖点参考 / 行动优惠参考（按品类分池）

第三层：规则（决定不出错）
产品保真规则 · 多图差异规则 · 单张收尾规则 · 无文字纯视觉规则
有目标语言时的文字要求 · 多语言排版约束

7.2 一条约束能省多少事

抄一段他们写在模板里的规则结构（复刻时直接照这个粒度写）：

## 1. 产品保真
· 商品主体的形状、比例、颜色、材质纹理、LOGO、型号文字，必须与参考图完全一致。
· 允许改变：环境、光线方向与强度、投影、背景、周围道具。
· 禁止改变：商品结构、配件数量、包装上的文字内容。

## 2. 多图差异
· 同一批 N 张图之间，构图、镜头、场景、文案必须至少 3 项不同。
· 禁止把同一张构图换配色重复输出。

## 3. 单张收尾
· 每张图必须自洽：有视觉重心、有留白、文字不压主体、无裁切错误。
· 文字层级清晰：主标题 > 副标题 > 说明文字，字号比约 3 : 1.8 : 1。
开源项目怎么用这套结构：把提示词从代码里彻底抽出来，做成 prompts/ 目录（YAML 或 MD），每个文件一个 key。
① 贡献门槛极低——社区提 PR 加一套"家居品类文案池"，不需要懂代码；
② 可版本化——git 就是天然的版本库，不必再在数据库里做一套回滚；
③ 可评测——配一个 benchmark/ 目录，30 个 SKU 的固定测试集，PR 跑一遍出分数，好提示词才能被合进来。这比任何 CONTRIBUTING 文档都有效。

7.3 测试集：比模板更重要

第一天就建一个 30 个 SKU × 5 个品类的固定测试集（家居 / 服饰 / 3C / 美妆 / 食品），每次改提示词或换模型，跑一遍打分：主体保真、文字正确率、版式合规、可用率（人工 1–5 分）。没有这个，所有"效果优化"都是玄学；有了它，社区才知道你的版本是变好还是变坏。

08密钥、配额与成本

去掉积分之后，开源项目真正要回答的是三个问题：钱谁出、密钥放哪、怎么防止被刷。

8.1 三种密钥模式（必须都支持）

模式谁付费配置方式适用
全局 Key部署者.env 的 OPENAI_API_KEY / GOOGLE_API_KEY 等个人自用、小团队内部、公开 Demo
用户自带 Key（BYOK）每个用户前端设置页填写 → 服务端 AES-GCM 加密入 user_api_keys → 调用时解密共享实例、社区公开部署
本地模型自己出电费OpenAI 兼容端点（Ollama / vLLM / ComfyUI 网关）内网、数据不出门、零成本实验
BYOK 的三条铁律：① 密钥永不回显（前端只显示 sk-****abcd）；② 密钥永不进日志（统一在 HTTP client 层脱敏）；③ 密钥永不进前端 bundle（所有调用走服务端代理，浏览器不直连模型厂商）。第三条最容易被开源项目违反——一旦违反，等于把所有人的 Key 公开。

8.2 配额：按张数，按天，按用户

# .env 里就四个数，够用了
DAILY_QUOTA=100          # 每人每天最多出多少张
MAX_BATCH=15             # 单次任务最多多少张
MAX_CONCURRENT_JOBS=3    # 单用户同时跑几个任务
GLOBAL_DAILY_BUDGET=5000 # 全站每天总张数（熔断用，防跑飞）
  • 不是一个阈值，是四层：单次、单日、并发、全站。少任何一层都有绕过路径。
  • 预留 + 结转：提交时按最大张数预留，成功后结转、失败后释放——这是唯一能防住"并发 10 个任务把额度打穿"的做法。
  • 超限要有话说：返回"今日 87/100，本次需要 4 张，还差 1 张"，而不是一个 429。
  • 管理员可调：后台能单独给某个用户放宽，不用改 .env 重启。

10八个真难点与破解

#难点表现破解
1商品保真LOGO 变形、材质变塑料、配件多一个参考图语义顺序 + 硬约束段首尾各一次 + 出图后视觉回读比对三项，不达标重跑
2中文文字渲染错字、糊字、繁体混入文字不要交给生图模型"画"，改为画布文字层后置合成；生图时只留占位区域
3多图一致性一套 8 张像 8 个品牌先定"整体设计规范"再逐张生成（两阶段就是为此）；色板/字体/光线写成规范段
4规划 JSON 不稳定输出带 markdown 包裹、字段缺失强 schema + few-shot + 容错解析（parse→截取→降级纯文本）+ 失败重试 1 次
5SKU 一致性同款不同色，颜色串到别的 SKUSKU 参数结构化；一次任务只换一个变量；局部替换用掩膜而不是整图重画
6共享实例被刷公网部署三天后被当免费 API 用ACCESS_CODE 准入 + 四层配额 + 全站日熔断 + 单 IP 限速，四道一起上
7密钥泄露Key 出现在日志、前端 bundle、错误堆栈里统一 HTTP client 层脱敏 + 加密存储 + 前端永不直连厂商 + CI 扫描 sk- 模式
8画布工程复杂度图层、文字、导出、撤销，越做越像 PS克制：只做"改字、换图、挪位置、导出"四件事；分层与 PSD 放 Phase 3

11开源版的差异化

收费产品拼"效果 + 便宜"；开源项目拼"可控制"。六件事别人做不到，你能。

① 数据不出门

商品图是卖家的核心资产。SaaS 再好，工厂和品牌方也不敢把未上市新品传上去。自部署 + 本地模型这条路线，只有开源能给。

② 提示词可改

PicsetAI 能改，但只在它自己的后台里改。你能改到代码层：某个品类的保真规则、某平台的合规话术，改完立刻生效并可提交上游。

③ 模型可换

今天 nano-banana，明天 Seedream，后天某个新模型——路由层一改就换。SaaS 用户只能等厂商排期。

④ 可嵌入自己的流程

接到自家 ERP / 商品后台 / 上新流水线里，点一下出图。这是纯工具型产品做不到的位置。

⑤ 评测透明

公开 30 SKU 测试集与打分脚本，任何人都能验证"这版是不是比上版好"。信任来自可验证，不来自宣传页。

⑥ 中文电商语料

详情页 16 模块、平台尺寸规范、广告法避坑——这些"土知识"是英文开源项目永远不会做的部分。

一句话定位

不做"又一个 AI 商品图工具"，做「可自托管的电商视觉生产线」：一张实拍图进去，一套可直接上架、可二次编辑、带平台尺寸的素材包出来；提示词、模型、数据全在你自己手里。
对外一句话：Self-hosted AI product-image pipeline. Bring your own model, own your prompts, keep your data.

12许可、合规与治理

12.1 许可证怎么选

方案适合代价
Apache-2.0想被商用、被集成、被大公司用别人可以拿去开 SaaS 不回馈
AGPL-3.0想防"云厂商直接托管赚钱"企业法务会犹豫，个人开发者不介意
MIT + 提示词 CC BY 4.0想最大化传播与贡献几乎没有约束，全靠社区口碑
建议：代码 Apache-2.0（带专利授权，企业敢用），prompts/ 与 benchmark/ 单独 CC BY 4.0（方便被引用、被二次分发）。两份许可写在 README 顶部，别让人猜。

12.2 合规责任边界

项要求开源版怎么落地
生成内容标识《人工智能生成合成内容标识办法》要求显式 + 隐式标识默认开启：导出图写入元数据水印 + 角落标识，后台可配文案位置；README 明确"部署者需自行确认所在地法规"
内容审核公开服务需对输入输出审核做成可选插件（plugins/moderation/），默认关闭 + 启动时提示；不预置任何厂商 SDK
肖像权AI 人像可能涉及真人相似度提示词默认禁止生成"某明星/网红"；模特库只用授权素材；上传人物图需勾选承诺
版权与所有权生成物归属README 写清：代码归项目，产物归使用者，模型条款由使用者与厂商自行约定
广告法文案可能含"最""第一"文案池预置合规词库 + 生成后扫描提醒（工具不背锅，但要提示）
数据安全用户素材是商业机密默认不落训练、存储可配保留期、一键清空；不做任何 telemetry（或默认关闭并明示）
参考图侵权"爆款复刻"天然有风险协议提示 + 技术上将复刻限定为"版式/配色/构图语言"，提示词显式排除品牌 LOGO 与原创插画

12.3 社区治理的最小配置

  • CONTRIBUTING.md：怎么加一个品类预设、怎么跑 benchmark、PR 必须附带分数变化。
  • prompts/ 与代码分离：提示词 PR 走轻量 review（一人 + CI 分数），代码 PR 走两人 review。
  • benchmark/：固定 30 SKU + 打分脚本 + 基线分数表，接入 CI。
  • docs/：部署（三种形态）、BYOK 配置、常见报错、成本估算表。
  • 不做的事：不做认证、不做"企业版阉割"、不在文档里塞任何推广——开源项目的信任一旦打折就回不来。

B附录：验收用例

  1. 冷启动：全新机器 git clone && docker compose up，不配任何模型 Key，能进站、能看到示例；配了 Key 才能生成，且有明确提示。
  2. 重复提交：同一 client_job_id 连点 5 次，只生成 1 个 job。
  3. 分析失败：LLM 返回非 JSON / 超时，前端展示可重试态，配额预留全额释放。
  4. 确认页超时：停在"确认规划"10 分钟不回，任务自动取消、释放预留。
  5. 部分失败：4 张里 1 张失败，交付 3 张、按 3 张结转、单张可重试。
  6. 供应商故障：主链路 500，自动切兜底链路，用户侧只见"稍慢"，最终成功。
  7. worker 崩溃：kill 掉 worker 进程，重启后卡在 generating 的 job 被标记失败并释放预留，不重复占额度。
  8. 配额并发：额度剩 4 张，同时提交 3 个"各 4 张"的任务，只有 1 个成功，其余明确提示剩余量。
  9. 密钥安全：抓取前端 bundle、日志、错误响应，均不含明文 Key；用户 Key 接口只返回掩码。
  10. 画布恢复：刷新页面后图层、位置、文字内容完整恢复。
